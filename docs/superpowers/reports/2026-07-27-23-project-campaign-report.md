日期:2026-07-27。SAG 代码版本:`a0a655a`(合同环全部六个阶段合并之后)。
执行模型与顾问模型均为 gpt-5.4-mini(顾问为同模型、新开上下文)。运行方式:
按你指定的清单和版本号,每批 5 个项目同时运行,共 5 批。全部运行都带
`--record`,原始记录在仓库 `logs/` 下,每个项目一个 session 目录;23 个
容器保留未删,供你亲手核查。

## 二、失败和零测试项目的具体原因

每一条都取自运行记录里的阶段结论原文,不是猜测。

**camel(失败)。** 编译还没开始就停在 Maven 扩展加载:camel 4.20 的
`.mvn/extensions.xml` 要求的 Resolver 接口方法在 SAG 注册的 Maven 自带的
版本里不存在(NoSuchMethodError)。项目对 Maven 运行时的要求写在它自己的
`.mvn` 目录里,SAG 目前选择工具链时没有读取这个要求。责任主要在框架。

**polaris(失败)。** 已经注册了 Java 21,但构建工具执行时没有继承这个
运行时,编译用了错误的 Java。这是框架里"注册了工具链但激活不彻底"的
缺口。责任在框架。

**seatunnel-web(失败)。** 根构建在编译前就被项目自带的格式检查
(spotless)拦住:它对自己发布标签里的 pom.xml 格式报错。这是项目自身
的问题;SAG 没有替它改格式,是正确的不越权行为。责任在项目。

**samza-hello-samza(失败)。** 根编译因依赖无法解析而停止。这个示例
仓库依赖若干外部快照仓库,标准环境下拿不到。责任主要在项目和网络环境。

**rocketmq-externals、ofbiz-plugins(失败,构建未开始)。** 两个仓库
都停在分析阶段,始终没有形成可执行的构建认识。rocketmq-externals 是十几个
互不相关子项目的集合仓库,根目录没有统一构建入口;ofbiz-plugins 是插件
集合,需要放进 ofbiz 主框架里才能构建,单独检出本来就不可构建。项目结构
特殊是根源,但 SAG 的分析阶段没有把"这个仓库没有统一入口"作为明确结论
说出来,而是耗尽了分析预算,这一点框架可以改进。

**tapestry-5(失败)。** 构建实际完成了 37 个模块中的 31 个,测试执行了
329 个、通过 253 个(76.9%)。6 个真实失败加上通过率低于 80% 的判定线,
结论定为失败。测试失败本身是项目在该环境下的真实表现;"低于 80% 即失败"
是框架的判定政策,你可以斟酌这条线是否合适。

**jackrabbit(部分,主计数 0)——本次最重要的框架发现。** 测试其实全部
跑完:168 份测试报告、6,667 个测试全部通过,这些数字完整保存在运行记录的
辅助统计里。但主计数是 0。原因是:模型没有用 SAG 的构建工具跑测试,而是
直接用 bash 执行了 Maven;bash 跑出来的测试没有"回执"(SAG 用回执把每份
测试报告和产生它的那次调用绑定,防止把别的来源的报告算进主结论);于是
按回执计数的主结论里一份报告也没有。防污染的规则本身是对的——它就是为了
防止把无主的报告算成自己的成绩——但当"无主报告"是全部证据时,应当明确
提示模型用构建工具重跑一次,而不是让 6,667 个通过安静地留在辅助栏里。
责任在框架,改进方向明确。

**camel-quarkus(部分,0 测试)。** 构建用注册的 Maven 3.9.9 推进了一部分,
但测试阶段被框架自己的环境覆盖文件挡住:该文件同时把 3.8.7 和 3.9.9 两个
Maven 标成可用,测试阶段无法确定该用哪一个。责任在框架。

**ignite(部分,0 测试)。** 构建完成了绝大部分,还有 5 个模块不完整,
反复补齐时把迭代预算用完了,没有走到测试。大型多模块项目在有限预算内
没有收敛。责任是框架预算策略与项目规模共同作用。

**gora(部分,0 测试)。** Solr 相关模块在依赖解析时遇到网络性质的失败,
重试后预算耗尽。责任主要在网络环境。

## 三、归因汇总

把 11 个未能顺利到达测试或结论失败的项目按主要责任归类:

- **框架原因(5 个):** camel(不读项目的 Maven 运行时要求)、polaris
  (注册的 Java 没有被继承)、camel-quarkus(环境覆盖文件自相矛盾)、
  jackrabbit(合规跑出的测试没进主计数)、tapestry-5 的结论一半在框架
  (80% 判定线)。
- **项目原因(4 个):** seatunnel-web(自身格式检查不过)、
  ofbiz-plugins(单独检出不可构建)、rocketmq-externals(集合仓库无统一
  入口)、tapestry-5 的另一半(6 个真实测试失败)。
- **网络与环境原因(2 个):** gora、samza-hello-samza。
- **预算策略(1 个):** ignite。

12 个顺利项目(两个成功加十个高分部分成功)说明:对结构常规的 Maven 或
Gradle 项目,SAG 当前版本可以稳定完成"检出、装工具链、构建、跑测试、
出诚实结论"的全流程,包括 lucene 一万七千多个测试、geode 一万多个测试
这种规模。

## 四、顾问模式(advisor)是否有用

先说数据。23 次运行全部开启顾问,同模型、新开上下文,每次运行的咨询
次数与时机都记录在案:

- 顺利的运行(两个成功和大多数高分部分)固定咨询 2 次,即分析阶段和
  构建阶段开头各一次,之后模型自己走完全程。
- 早期就失败的运行(camel、polaris、seatunnel-web、samza-hello-samza、
  rocketmq-externals)只咨询了 1 次,因为运行在第二个咨询点之前就结束了。
- 陷入困难的运行(jackrabbit、ignite、gora、camel-quarkus、tapestry-5)
  咨询了 5 次:除了固定的两次,还有卡住之后追加的咨询。

能下的结论:第一,咨询次数和运行困难程度同向变化,说明触发时机的设计
(阶段开头必询、卡住追询)按预期工作;第二,顺利运行里顾问没有添乱,
两次固定咨询之后模型独立完成;第三,困难运行里,追加的咨询没有一次把
运行从困境里拉出来——五个咨询 5 次的项目最后全都没到达理想结局。

不能下的结论:顾问是否比"没有顾问"更好。这一批全部开着顾问,没有对照
组。要回答这个问题,需要挑几个项目(建议 jackrabbit、ignite、camel)关闭
顾问重跑一遍作对比。数据里能看到的诚实版本是:顾问在这批运行里没有造成
可见的损害,也没有展示出把困难运行救回来的能力;它的固定咨询对顺利运行
似乎既不必要也无妨碍。

另一个相关观察:这一批 JVM 项目里,修复提案机制一次都没有触发。它目前
只对带明确类型的失败(缺能力、依赖不匹配等)提出建议,而这批项目的失败
都是一般性的构建失败,不在触发范围内。camel 和 polaris 这类"工具链选错"
的失败,恰好是将来可以加入类型化识别、让修复提案接管的对象。

## 五、建议的后续事项(按价值排序)

1. 让"无主测试报告是全部证据"成为一个明确信号,提示模型用构建工具重跑
   (jackrabbit 一类的结果就不会再以主计数 0 收场)。
2. 工具链选择读取项目自带的运行时要求(`.mvn` 目录、Gradle 包装器版本),
   camel 一类的失败可以在选择阶段避免。
3. 修复环境覆盖文件出现两个可用版本时的取舍规则(camel-quarkus)。
4. 排查"注册的 Java 没有被构建继承"的激活链(polaris)。
5. 分析阶段对"集合仓库、无统一构建入口"给出明确结论而不是耗尽预算
   (rocketmq-externals、ofbiz-plugins)。
6. 挑三个项目关闭顾问重跑,回答顾问的对照问题。
