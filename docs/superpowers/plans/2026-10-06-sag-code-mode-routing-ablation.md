# SAG code mode：工具入口与编排消融计划

日期：2026-10-06（America/New_York）。状态：**清理完成，方案待审阅；本次未修改 SAG 实现，未启动新实验。**

本计划接续 [10 月 2 日计划](2026-10-02-sag-ten-project-code-mode-ablation.md)，修订后续 code mode 的设计与实验。旧计划、冻结协议和原始结果继续保留。本文件不改变已完成批次的分组、评分或结论。

目标是让小模型用 SAG 完成 build 和 test，并降低完成任务所需的模型往返和 token。SAG 仍是一套面向 setup 的 harness。Phase、执行记录、物理验证和独立验收器继续负责原来的工作。

## 1. 已知事实与本次问题

上一轮正式对照为 10 项目 × 4 组 × 2 次，共 80 次。开放 code 的 40 次运行均未调用 code。C−A 与 D−B 的项目等权总 token 分别增加约 11.11% 和 14.31%。这些结果说明原来的可选入口没有产生预期收益，**不能证明已经执行的代码编排更耗 token**。[结果及边界](../../../output/sag-ten-code-mode-20261002/formal-parallel/analysis/readout.md)

当前实现有三个需要检验的设计选择：

1. 所有原生工具仍可直接调用。模型不需要学习另一种调用方式也能完成任务。
2. `CodeTool` 明确建议简单操作优先使用原生调用。现有示例也只有一次读取，没有展示减少往返的用法。
3. 参数说明来自原生 schema。若直接隐藏原生工具，却不搬运完整契约，模型将失去参数、返回值或修复声明的必要信息。

这些是可核对的接口事实。它们分别对零采用率产生多少影响，尚未得到因果证明。不能把额外 token 全部归因为“工具描述太长”，也不能先假定强制编排一定更好。

本轮只回答三个问题：

- **采用：**明确编排用途，或者收窄直接调用入口，能否让模型正确使用 code？
- **效率：**在完成相同 build/test 要求时，编排能否减少模型请求、中间结果输入和总成本？
- **边界：**哪些行为适合代码处理，哪些行为仍需要 Actor 逐步判断？

## 3. 设计：控制调用路径，保留任务能力

### 3.1 只区分两类入口

| 工具 | 作用 | code-only 候选中的位置 |
|---|---|---|
| `project`、`search`、`file_io`、`build`、`bash` | 环境、发现、读取、修改和执行 | 保留原实现，通过 `tools.NAME(args)` 调用 |
| `phase`、`report` | 阶段交接与报告交付 | 保留原生入口，不允许在脚本内调用 |
| `advisor` | 咨询 | 只有原本启用 Actor 咨询时才保留原生入口；本轮主比较关闭 Advisor |
| `code` | 编排已有工具 | 原生入口；不能递归调用自身 |

本轮针对 setup 流程，不改造旧 `run_task` 流程，也不重新加入 `manage_context`。

需要把“当前能执行”与“向模型声明为原生工具”分开。现有 `_tool_available()` 同时服务 schema 和执行检查；不能在其中直接把隐藏工具判为不可执行，否则脚本里的同一工具也会被禁用。

最小实现是在现有 schema 投影处增加路由筛选，并在派发处识别原生调用与已有的 `parent_program_id`。保留同一工具注册表、同一参数校验和同一执行入口。暂不建立新的通用工具注册框架。

code-only 下，隐藏的原生调用在执行前被拒绝，并返回准确的代码调用方法。不得暗中把原生调用转换为脚本后记作“Actor 采用了 code”。所有拒绝和恢复都计入运行轨迹与消耗。

### 3.2 工具说明不能跟着入口消失

从现有工具定义生成脚本契约，不维护第二份手写参数表。至少保留：

- 工具用途、参数名称、类型、枚举、必填字段和默认行为。
- 当前修复上下文要求的 `repair_intent` 等参数；与原生 `_repair_aware_schema()` 的有效结果一致。
- `text`、状态、错误、`facts`、`receipt_view`、`receipt_view_path`、完整输出路径和 ref 的语义。
- 分页的可见范围、完整性与下一页入口。`null` 表示不可得，不能改写成零或成功。
- pending、取消、超时、阶段关闭和证据封存的行为。

SAG 目前只有少量主要执行工具，第一轮将它们的完整契约直接交付，不引入大型工具搜索或模型压缩。原生与代码契约保留相同语义，格式可以不同。混合模式不要再复制一遍完整 schema，只补脚本调用方式和返回契约。

检查必须落在**真正发送给 provider 的 payload**上，而不只检查 Python 中间对象。code-only 下还要移除系统提示和错误提示中的无效原生调用指导。

### 3.3 提示只覆盖 build/test 中有价值的编排

给混合与 code-only 两组相同的编排指导，并明确允许单工具脚本。指导分三类：

| 情景 | 预期行为 | 不能提前替模型决定的事 |
|---|---|---|
| 已知多个配置或 receipt 路径 | 一次读取并输出必要事实、来源及缺失项 | 不能注入评测答案或尚未发现的项目特定路径 |
| 完整日志太长，需要搜索或翻页 | 按工具返回的游标继续读取，筛选目标内容，同时保留完整输出入口 | 不能把页内没有命中当成全日志没有错误 |
| 后续调用参数可从前一结果直接得到 | 在脚本中完成这段确定性数据流 | 出现新错误或需要解释源码时，先把证据交回 Actor 判断 |

示例必须使用当前真实参数和返回字段，并通过执行夹具。重点展示“读取后按实际 ref 继续读取”与“多份结果提取必要字段”，不再只展示单次读取原样输出。

不要强制凑够若干子调用，也不要要求用脚本自动修复未知错误。code-only 的“统一入口”允许只有一个子调用；这种包装会单独计量，不能自动算作编排收益。

### 3.4 继续使用现有执行与证据边界

每个子调用仍经过 `_execute_action_step()`。权限、修复声明、环境检查、无进展检测、receipt、工作树记录及物理验证继续生效。

- 子调用顺序执行。暂不加入子工具并行，以免把减少模型往返与运行并发混在一起。
- 遇到 pending/job barrier、取消、预算耗尽或封存，停止派发后续子调用。`catch` 不能绕过这些边界。
- 脚本失败保留已完成行为，不自动重跑整段程序；后续恢复明确选择尚未完成的动作。
- 脚本选取的正文进入模型上下文；完整子结果归档。harness 始终附真实状态、失败或 pending 摘要及可读引用，不能被 `text()` 过滤掉。
- 脚本完成不认证 build/test。最终评分仍来自原始、字节绑定的物理证据。
- 不新增跨阶段 JavaScript store，不开放宿主文件、网络、进程或 provider 凭据。已有工具仍可按其原权限执行相应工作。

## 4. 三组对照与固定条件

| 组 | 模型直接看到的工具入口 | 工具能力 | 要比较的效果 |
|---|---|---|---|
| N：native | 原生执行工具、phase、report | 现有能力 | 当前原生基线 |
| H：hybrid | N 的入口，加 code；使用新编排指导 | 与 N 相同 | 提供明确用途后是否主动采用 |
| R：code-only | code、phase、report；执行工具的完整脚本契约 | 与 N 相同 | 统一执行入口的整体效果 |

H−N 测量的是新可选编排方案的总效果。R−H 测量的是取消直接执行入口、随之调整声明格式后的总效果，不能写成纯粹“隐藏几个工具”的单独因果效应。若后续要拆解 schema 字节数的影响，再设计单独实验，不在本轮追加组合。

原生组继续允许一次模型响应发出多个工具调用。不能把基线改成只能单步调用。旧 C/D 的 legacy 提示保留在原冻结快照中，不混入本轮分母，也不充当新 N 的同期结果。

三组共同条件：

- Actor 使用既有 `gpt-5.4-mini` 配置：temperature 0、输出上限 10,000，不新增 reasoning 设置。
- Advisor 关闭，接口、提示和 gate 均关闭。先隔离路由因素；本轮不重做 Advisor 的四组交互。
- 共同使用 H1 `relevant` 交接，沿用 6,000 字符预算。H1 是已有共同基础，不再次宣称其普遍最优。
- 相同项目 commit、任务文件、CI target、requirements、依赖策略与公共验收器。正式命令同时绑定 acceptance task 和 CI target。
- 同一候选源码快照与共同镜像，所有组都包含运行器依赖；组间只改变声明的路由配置和相应提示。归档 Git 状态、源码 hash 和差异，不依赖未提交工作树的未来状态。
- 每次沿用 `max_iterations=150`、150 个逻辑工具调用、7,200 秒、4 CPU、8 GiB、无额外 swap。参数来自上一轮冻结预算，不按本轮结果调节。模型迭代上限不冒充严格的 provider 请求上限：实际请求及其重试另外完整计量。
- 原生动作和代码子动作使用同一逻辑调用口径；父 code 包装不再加算一次子动作。无效请求和零子调用程序仍受原有模型请求、时间和运行器预算限制，不能形成无限免费重试。

不同时修改 JDK 策略、修复规则、phase、验收要求、Advisor、缓存预热或工具并发。确需修复共同正确性问题时，另记版本，三组一起更新后重新冻结。

## 5. 先做工程验证，再跑三个项目

### 5.1 工程验证：不调用模型

复用已有 code runtime 和 Docker 夹具，补以下有实际风险的检查：

1. N/H/R 最终 provider payload 正确。R 中隐藏工具仍可从脚本执行；禁用或封存的工具不能因脚本而重新获得权限。
2. 三组的工具参数、修复字段、返回字段与错误语义一致。系统提示和错误恢复示例不要求调用不可见入口。
3. 原生批量调用与脚本调用读取同一组夹具，得到相同事实与完整引用。依赖读取链可在一次 code 调用内完成。
4. 工具失败、分页未完、引用失效、空值、长单行 JSON 和 Unicode 不被误判为完整成功。
5. pending、取消、重复副作用、worker 失败及封存路径保持原有边界。伪造脚本输出不能把任务判绿。
6. 父子调用、模型请求和 token ledger 可对账。子结果不会悄悄重新全部进入下一次模型请求；失败摘要也不会被悄悄裁掉。

不以单元测试证明真实模型会采用 code。工程门槛通过后才进入完整任务试跑。

### 5.2 完整任务试跑：18 次

选用既有十项目中的三项，不改任务来制造 code 优势：

| 项目 | 选择依据 | 已冻结任务 | 上轮原生基线时间，仅用于排程 |
|---|---|---|---|
| Commons DbUtils | 小型、单模块，提供最简单的对照 | `clean test`；不要求主 JAR | 约 5.0–5.8 分钟 |
| Commons Net | 中型、单模块，包含测试、打包和安装 | `clean install` | 约 7.5–7.8 分钟 |
| Gson | 中型、多模块，要求更复杂的范围与结果读取 | 沿用冻结的 `verify javadoc:jar` 等完整规定行为及 Java 21 | 约 9.5–10.1 分钟 |

这三项在上一轮实际 CI 验证结果中均有可评分的范围和测试聚合数量基线。选择依据是任务差异、可核对的证据和运行长度；不是从 code 采用者中挑选。它们全部已经参与过旧设计开发，属于开发集。[实际 CI 判定](../../../output/sag-ten-code-mode-20261002/formal-parallel/analysis/behavior-and-ci.json)

每项 N/H/R 各两次，共 `3 × 3 × 2 = 18` 次。两次重复沿用上一轮的最小重复规模，用于发现偶然行为；它不构成统计功效或可靠性证明。

使用六种顺序，平衡三种配置在块内的位置：

| 项目 | 第一次 | 第二次 |
|---|---|---|
| DbUtils | N → H → R | R → H → N |
| Net | H → R → N | N → R → H |
| Gson | R → N → H | H → N → R |

同一项目的运行不并行。最多三个不同项目同时运行，仍先检查 Docker、RAM、磁盘和已有控制器；新容器、挂载和依赖缓存条件按同一协议处理。沿用宿主和 Docker 至少 32 GiB 空闲、并覆盖剩余归档预留的检查，内存按即将派发的一整波任务预留。记录执行顺序、资源样本和实际 cache usage，不把“相同模型”当作缓存条件相同的证明。

完成每个项目的完整任务，包括报告交付、封存和公共验收。出现执行失败时保留原结果；基础设施或证据错误需先保护现场，再判断是否中止派发。修订版本的数据单列，不覆盖前一版本，也不以失败后补跑的较好结果替换原结果。

### 5.3 扩展门槛

先核对真实行为，再决定是否值得扩大：

- 工具可达性、父子调用和归档检查全部通过；没有因为包装而新增的错误成功判定或丢失证据。
- R 的执行类动作确实走子调用；不能存在原生旁路或 harness 代做。
- 真实运行中出现可以回放的多调用链或中间结果筛选，才说明测到了编排机制。如果 R 全部只是单调用包装，则先解释原因，不立即跑大批次。
- H 的低采用率或零采用率是有效结果，不通过追加提醒或删去未采用运行来“纠正”。
- 对新的完成率下降、提前结束、异常低 token 和较长恢复循环逐条归因。不能仅因平均 token 下降而通过。

满足工程和机制门槛后，冻结下一阶段方案：既有 10 项目 × N/H/R × 2 次，共 **60 次**。三项开发项目仍留在表中，另披露其余七项；整个十项目集合已用于既往设计，不能称为全新留出验证集。

FreeMarker 不进这次快速试跑。后续十项目阶段若保留它，必须独占运行并沿用统一资源配额；OOM 作为资源限制下的真实结果保留。同条件重跑单列诊断，不替换正式行。

60 次是后续确认阶段的计划规模，本次不启动。Advisor 开启后的交互和本地弱模型泛化另行验证，不把它们捆入当前三组矩阵。

## 6. 怎样衡量采用、成功与成本

每次运行输出一行汇总，并提供原始证据链接。分母固定为已分配并派发的尝试，普通失败和未采用 code 的运行均保留；尚未派发的槽位另列。主表不按成功或采用行为事后筛选。

| 维度 | 必须报告的指标与口径 |
|---|---|
| 完整任务 | `complete / incomplete / unavailable`；第一项阻塞要求、停止原因、人类干预和归档完整性 |
| Build | 要求级 passed/failed/not_run/unavailable，模块完成数/要求模块数，主 class 与主 JAR 数及其范围 |
| Test | 实际 ran、passed、failed、errors、skipped，报告范围、缺失项与重试处理；严格采用现有 evaluator 口径 |
| CI 对照 | 仅在当前 verifier 接受同一任务绑定和证据时评分；范围、聚合数量和用例身份分别报告 |
| code 采用 | 有实际 code 程序的运行数/已派发数；程序数、子调用数、拒绝数、脚本失败和恢复回合 |
| 编排行为 | 单调用程序比例；实际执行至少两个不同逻辑动作的程序数；其中依赖读取与结果筛选的可回放案例 |
| 模型往返 | Actor 请求总数、各阶段请求数；原生批量调用宽度和 code 子调用宽度均报告 |
| Token | provider 实测 input、cached input、uncached input、output、total；cached 是 input 的子集，不能重复相加 |
| 上下文 | 实际 provider payload 中的工具说明和结果字节数、程序输出字节数、是否再次送入完整子结果；字节数是解释指标，不冒充 token |
| 时间与资源 | 完整无人干预运行时间、模型等待、工具时间、运行器开销、峰值内存、OOM、磁盘和容器状态 |

至少两个子调用只证明“组合了调用”。独立动作原生批量也能在一次请求中完成，因此不能直接等同于节省一次模型往返。声称减少往返时，必须给出对应的数据依赖与原生对照轨迹。冗余读取、重复运行已完成构建或空操作不算有意义的组合。

主分析按项目与重复编号配对，再按项目等权汇总。三项目试跑只做描述性分析，不宣称统计显著。十项目阶段报告项目级不确定性与逐项目结果，不把 60 次运行当作 60 个独立项目。

成本同时给出所有尝试的总消耗，以及双方都完成相同任务的配对子集；后者明确列出样本数和被排除项目。失败消耗不会从主表消失，较少 token 也不能抵消更少的 build/test 工作。未测真实计费时，不用总 token 推断美元费用。

当前三项目的 CI 聚合数量相同，不代表逐用例身份相同。上一轮十项目的跨运行 case identity 都不可评分；本轮不得换个汇总标题就声称 full CI parity。

## 7. 实施顺序和交付物

| 顺序 | 工作 | 主要位置 | 完成证据 |
|---|---|---|---|
| P0 | 固定当前事实、有效工具契约和最终 provider payload 样本 | 现有 formal 归档与新候选目录 | 基线清单、旧零采用率复算、差异列表 |
| P1 | 分开工具执行资格与原生声明；加入三种路由 | `agent/react_llm.py`、`agent/react_engine.py`、`agent/agent.py`、配置 | 最终 payload 与派发边界检查；隐藏工具仍可合法执行 |
| P2 | 生成完整代码契约；改进 build/test 编排指导和示例 | `tools/code_tool.py`、prompt builder/YAML、`agent/code_program.py` | 参数、修复字段、返回格式、分页和错误示例实际通过 |
| P3 | 验证共同执行链与计量；只补缺失检查 | 现有 runtime、原生消息、receipt 和预算夹具 | 工程检查及 Docker 证据链通过，源文件和镜像冻结 |
| P4 | 运行三个项目的 18 次完整试跑 | 新 protocol、既有并行控制器和归档器 | 18 次完整记录或明确未派发原因、独立评分与用量对账 |
| P5 | 检查采用机制与任务完成，决定是否进入 60 次确认 | 派生分析与 dashboard 独立批次 | 逐项目表、轨迹对比、失败归因、扩展决定 |

代码默认值不因试跑而自动改变。旧批次仍使用旧源码快照和旧协议；新实验目录独立命名。若修改路由后模型只产生更多单调用包装或恢复循环，应保留负结果，并允许结论为“当前任务不适合统一编排”。

只改完成本轮比较所需的位置，不重写 phase 状态机、不另建 verifier、不迁移到另一套 Agent SDK、不新增模型或项目。

## 8. 参考依据与适用边界

以下是接口设计依据，不是 SAG 已获收益的证明：

- Pi 的 [`codemode.mode`](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/settings.md#tools) 区分 `on` 与 `only`。项目已保存的固定源码为 `a276dabe57911253350bffb93cb7d7aff6a73261`；其中 [`prepareCodemodeLoadout`](https://github.com/earendil-works/pi/blob/a276dabe57911253350bffb93cb7d7aff6a73261/packages/coding-agent/src/extensions/codemode/tool.ts) 分别处理工具可调用集合和原生声明。见 [来源封存](../../../output/code-mode-plan-20261002/pi-source/provenance.json)。
- [Codex 配置](https://learn.chatgpt.com/docs/config-file/config-reference)公开了 direct-only 与排除嵌套的命名空间；[hooks 文档](https://learn.chatgpt.com/docs/hooks#tool-calls-from-code-mode)说明嵌套工具仍经过调用前后控制。这支持保留 SAG 的共同调度边界，不能据此声称所有 Codex 默认都采用 code-only。
- [OpenAI Programmatic Tool Calling](https://developers.openai.com/api/docs/guides/tools-programmatic-tool-calling#guide-routing-when-both-modes-are-available)要求为可预测的数据处理与需要逐步判断的操作划清路径。这里只借鉴指导方式，不更换 SAG 的 API 或模型能力。
- [Anthropic Programmatic Tool Calling](https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling#the-allowed_callers-field)区分调用方式，并提醒调用提示不等于执行安全边界。SAG 的权限与验收仍由执行端负责。
- [Cloudflare Code Mode](https://blog.cloudflare.com/code-mode-mcp/)用两个入口承载大型 API。SAG 的工具规模更小，本轮不直接套用它的 token 节省比例，也不为此引入大型动态发现系统。

联网资料核对时间为 2026-10-05；后续实现以前述固定源码及本项目实际工具契约为依据。当前 `gpt-5.4-mini` 结果只支持该模型和这些任务下的结论，不能直接外推到本地弱模型或所有 CI 项目。
