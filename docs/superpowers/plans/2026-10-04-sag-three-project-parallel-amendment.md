## 并行安排

并行单位是不同项目。同一项目的组别按原顺序执行。保留预先确定的 `ABDC/CDBA`、`BCAD/DACB` 及其项目分配，不因结果重排。

按既有项目清单顺序，正式阶段固定分为四批：

1. Commons CSV、Commons Net、Commons DbUtils。
2. Tomcat Jakarta EE Migration、Sling Commons MIME、Creadur Whisker。
3. Commons DBCP、Gson、HttpComponents Core。
4. FreeMarker 单独运行；它包含跨 JDK 和 native 编译路径。

每批有四个执行位置。一个位置中的各项目可以同时跑各自对应的组；全部结束且归档通过后，才进入下一个位置。不用新项目或下一组填补提前空出的并行位。这样普通失败和提前结束不会改变其他项目的派发顺序。第二轮保留相同项目搭配，反转批次及项目顺序，组内次序沿用原调度表。

试跑只有两个项目，最多并行两个，共四波八次。正式阶段最多并行三个，共三十二波八十次。“波”不是新增样本：计分单位和重复次数不变。

并行调度表与检查保存在 `output/sag-ten-code-mode-20261002/parallel-preparation/`。新执行器复用现有 SAG runner 和归档核验器；15 项进程测试、三容器编译测试、采集故障及取消测试已通过。旧 SAG 归档的 2,098 个文件和 11 次 Actor 请求绑定也已复核。此次是执行设施验证，尚未启动四组模型试跑。详见该目录的 `validation.md` 与 `validation.json`。

旧串行 controller 仍有旧八次采用 gate，不能直接恢复旧队列。新入口为 `parallel_campaign.py`，输出到新的 `p2-parallel` 与 `formal-parallel` 目录，不覆盖旧数据。

## 资源和执行门槛

实测本机 64 GiB、18 CPU。确认没有运行容器和其他 OrbStack 虚拟机后，已将 Docker 内存配置从 16 GiB 调到 32 GiB；重启后 Docker 实报约 31.36 GiB。每个任务仍为 4 CPU、8 GiB，无额外 swap。不能用三个项目眼下内存占用低，代替三个容器的完整预算。

每个运行按完整 8 GiB/4 CPU 预留，客体至少保留 4 GiB/2 CPU 给系统。当前容量允许预留三个任务。4 GiB/2 CPU 是工程保护余量，不是统计或项目筛选阈值。若实际容量不足，按资源公式准备较低并发的固定安排，并在开跑前封存；运行中容量下降则停发复核，不悄悄改变某一组的条件。

宿主和 Docker 文件系统均保留 32 GiB，加上预估剩余归档空间。使用不同端口、容器、输出目录和项目缓存。所有组都记录同批运行项、资源样本和 provider 重试，保留 cached/uncached 用量。

已验证独立端口和状态、证据归档、采集失败停止下一波、正在执行任务受控收尾、控制器异常重启拒绝重复派发。测试发现并修复了 macOS 地址复用导致端口冲突预检漏报的问题；最终版已重跑通过，失败记录保留。小型 Java 样例不能证明实际项目没有 OOM 风险，也不能证明 provider 排队和四组指标采集正确；这些仍由 8 次真实试跑检查。

下一步先完成全部 H0/H1 结果及共享执行问题复核，再封存共同交接方案和 8 次试跑协议。新入口会校验采用决策、验证结果、控制器依赖及输入的哈希；缺少所需记录时拒绝开跑。试跑复核后才进入 80 次。

## 解释边界

并行会影响资源竞争、网络等待和 API 排队。四组都采用相同安排；本轮墙钟反映并行环境，不能直接减去先前串行结果来声称设计提速。按项目配对、重复反序并披露干扰，不能声称干扰完全消失。

继续执行已补充的停止审查：先看任务完成，再看相同完成情况下的成本。失败的低 token 不算效率优势，双方成功子集也不能替代全样本结果。详细规则见当前交接批次的 `analysis/early-stop-analysis-policy.md`。
