日期：2026-09-24。状态：A 候选的源码对照、实现、离线检查、12 次单步模型诊断、6 次多步续查及 16 次 offset 四组对照已完成；候选继续隔离，本轮新增 offset 提示不合入，未启动新构建。接续 [Token 归因与修复计划](2026-09-23-token-overhead-attribution-and-remediation.md)。

实施更新：A 候选已在隔离目录实现，85 项定向检查、129 项执行边界回归及真实归档读取检查通过。用户明确批准本批发送后，12 次模型诊断全部返回，无超时或重试，未执行返回的工具调用。可用的原日志查询从 0/6 增至 3/6，但三个查询的首批匹配范围均不含关键 warning；当前工具保留了后续分页入口，单步实验尚不能判断模型是否会继续读取。决定先做有界多步只读验证，暂不接入生产或推进 B/C。详见 [结果与局限](../../../output/evidence-navigation-ablation-20260924/report.zh.md) 和 [候选实现](../../../output/evidence-navigation-ablation-20260924/README.zh.md)。

多步验证追加：用户单独批准后，接续上述三个有效查询，共 6 次请求全部返回，无重试。没有模型动作正确沿 `Next search` 参数续页；两条转去请求任务要求的 toolpaths 交付，按只读边界停止，不能当成完整任务失败。另一条先用超出总匹配数的 `offset=1160`、`900` 连续空读，随后取消 offset、改变关键词，原始 warning 进入请求后才正确指出符号和位置。新增总 token 为 85,923；这是条件轨迹的用量，不是成本消融或项目成功率。下一步先单独验证分页单位与越界反馈的可用性，暂不扩大到完整项目。详见 [翻页验证报告](../../../output/pagination-qualification-dbcp-20260924/report.zh.md)。

Offset 消融结果：两个源文件的说明/空页反馈候选实现后，58 项定向测试通过。用户明确批准后，四组（控制、仅说明、仅反馈、两者）各 2 条轨迹，共实际发送 16 次请求，全部返回。四组均 2/2 将关键原文送入模型，新增空读均为 0、请求数均为 4。仅说明、仅反馈、两者的总 token 分别比控制组增加 0.56%、2.20%、2.78%。反馈确实让模型复制 offset=0 的重试，但没有减少请求；本轮不合入两个新增提示。所有组共同修正了 host 路径显示，不能与上批直接作因果比较；单状态、两次重复不支持普遍无效结论。详见 [完整数值与处置](../../../output/search-offset-ablation-20260924/report.zh.md)。

## 1. 本轮要回答的问题

SAG 是面向 build/test setup 的 harness。目标是让弱模型准确找到当前失败的原始证据，减少读错文件、重复搜索和重复交付的请求，同时完整保留任务要求与独立物理验收。

此前两个小项目的 prompt 对照完成了固定任务，但总 token 未改善；DBCP 的 12 次归档诊断有 11 次返回、1 次超时，失败摘要候选暂不接入。新摘要给出了原日志 L1248，模型仍把该行范围用于只有一行的 receipt 搜索派生文件。仅提供更多错误文字或更大的上下文窗口尚未解决来源混淆。

## 2. 从哪个 OpenCode 版本学什么

使用既有实验的 OpenCode **v1.18.32**，对应提交 `545f51d26cc39a907d2867492d498d9607ea5fa4`，不把最新版实现混入旧实验的因果解释。本次重新核对了此前保存的 11 个源码文件的 SHA-256；首轮重点阅读 `tool/truncate.ts`、`tool/shell.ts`、`tool/registry.ts`。完整来源见 [源码清单](../../../output/sag-opencode-token-study-20260924/opencode-source/source-manifest.json)。

| 已读取的实现 | 值得借鉴的做法 | SAG 的适配边界 |
|---|---|---|
| `truncate.ts` | 超限后保存全文，返回预览、完整文件路径、截断标记及分页/搜索提示 | 保存原始字节，读取指令须对应 SAG 实际工具与容器路径；不照搬其默认字节/行阈值 |
| `shell.ts` | 输出过长时转入文件，返回尾部预览；同一次结果带退出码、截断状态和 `outputPath`；超时/中断使用单独说明 | 原始命令、实际运行时、退出状态和日志入口应可一起读取；命令结束与任务完成分别判断 |
| `registry.ts` 的插件工具适配路径 | 将文本结果和 metadata 整理成统一返回，并附带截断文件入口 | 复用 SAG 现有 `ToolResult` 和持久化层，减少各工具自行拼接互不一致的提示 |

这里借鉴的是工具执行记录与读取界面。已读代码中的 `metadata.exit`、`outputPath` 不足以建立 SAG 所需的测试 XML、模块、产物、目标提交和实际 JDK/Maven 的绑定；不能将其直接当成同等验收 receipt，也不能据此断言 OpenCode 整个产品缺少其他验证机制。

部分实现不能直接照搬：通用截断提示含“tool call succeeded”，未区分编译命令是否成功；它还会在 Task 工具可用时建议委派。SAG 应分别显示工具调用状态、命令退出状态与任务判定，不为此引入通用子代理流程。其七天输出清理策略也不能替代论文实验的封存保留规则。

已补读同版本的 Read/Grep、工具结果转模型消息和会话持久化路径，并封存 [五个源码文件及哈希](../../../output/evidence-navigation-ablation-20260924/opencode-source/source-manifest.json)：Read 在正文中提供路径、行号和后续 offset；Grep 按源路径展示；消息转换主要使用 `part.state.output`，一般 metadata 不会自动完整进入模型上下文。OpenCode 的一基 offset 和单行截断语义不能直接套入 SAG 的零基读取与字符续读。源码存在某项能力，不代表本批 OpenCode 轨迹使用了它。

## 3. SAG 的最小改动方向

### A. 将原始证据与读取入口放在一起

同一条当前失败信息中展示命令/cwd、退出或终止状态、实际运行时、原始日志 ref/path，以及能直接使用的现有 `search` 或 `file_io` 参数。带行号的 excerpt 必须紧邻其原始路径；对 `file_io` 使用文档规定的零基起点与右开区间，不把日志显示行号直接当调用参数。

读取派生结果时明确“本次读取的文件/来源”与“产生该失败的原始命令日志”。搜索成功仅表示取到了匹配内容，不能把父命令的失败改写为成功；派生输出也不能覆盖当前失败的原始入口。只携带已绑定的来源，缺失时明确缺失，不猜测 ref 或路径。

复用现有结果 metadata、lineage 与输出文件；先检查当前字段能否覆盖要求，再考虑最少的附加字段，不新建上下文管理工具或另一套证据存储。

### B. 给模型一个可读的 receipt 视图

底层 canonical receipt 继续保存完整的验证事实及引用；面向模型的展示由这些事实确定性生成：命令、状态、运行时、测试计数及口径、产物/报告入口、缺失项和原始日志入口。完整记录仍可读取。

不要把完整逐用例 JSON 默认为构建 warning 的搜索入口。需要逐用例证据时才沿其现有文件入口继续读取；所见是摘要还是完整记录、有哪些省略，都应明确标出。测试名含 `Warnings` 只能算文本匹配，不能被展示成 Maven warning。

这一步改的是读取展示，不删除 canonical receipt 字段、不放松大小或完整性校验、不改变成功标准，也不引入新的 LLM 摘要调用。让模型读懂短视图并不授予该视图判定权。

### C. 独立检查工具调用与交付开销

完整保留工具用途、必需参数、允许的 target 形式、行号单位、长行续读与执行边界。`ref:output_*` 这类错误先检查是否可做无歧义的兼容解析或返回具体可用参数，不能仅通过 JSON schema 就判为可执行。未知引用不能被悄悄换成最近日志。

DBCP 多步验证表明，虽然 schema 已解释 offset 是跳过的匹配数，模型仍出现过连续使用超大值的情况。已隔离实现并消融两个展示候选：明确匹配序号与源行号的区别；在匹配耗尽时提供同关键词的可选从头搜索参数。没有静默重置、单位转换、换来源或查询改写。真正零匹配、正常分页及参数语义保持原样。四组恢复结果一致，新增提示增加 token；本轮封存候选而不接入默认实现，不能拿历史失败代替本轮控制组。

`toolpaths.json` 重复写入是另一项协调开销。是否能由已验证的运行时注册状态交付应单独验证，不与证据读取改动捆绑；共同 benchmark 协议与独立版本核验保持一致。

## 4. 验证顺序和消融

1. **补齐源码与实际消息对照。** 每项记录 OpenCode 版本、源码位置、真实模型所见、SAG 对应代码，以及预期解决的具体错误。只做只读归档核验。
2. **先验证 A。** 以当前冻结 SAG 为基线，只改原日志/派生来源和读取入口的绑定。保持 prompt、完整工具 schema、Advisor 策略、模型参数和验收器相同；旧的未采纳摘要候选只作回归参考，不能当成已部署基线。
   多步验证确认原文可达，但模型正确翻页仍未通过；一条靠重新搜索取得关键诊断。匹配 offset 与越界反馈的四组恢复验证已完成，没有显示增量收益，因此不追加提示或搜索排序规则。归档适配器的 host 路径不一致已在四组中统一修正；该共同修改的独立效果未测量。后续若再验证恢复能力，应选新的独立错误状态，避免反复重跑单例挑选有利结果。
3. **A 决策结束后再验证 B。** 用单独条件改变模型所见 receipt 视图，区分来源定位收益与缩短 receipt 展示收益。C 同样另开条件。禁止一次改动全部层次后归因给工具设计。
4. **归档读取正确后再做两个小项目。** Commons DbUtils 与 Commons CLI 保留既有完整任务范围；DBCP 优先复用归档，不重跑长构建。沿用 gpt-5.4-mini，Advisor 设置固定，不引入 Terra；已有 OpenCode/Claude 记录不为这轮重新运行。

归档检查至少覆盖：长 Maven 日志的具体 warning、包含同名测试方法的单行 receipt、派生搜索后继续读取、失败后成功重试、原始引用不可用、Gradle 失败与中断/超时。合成边界用例只检查实现正确性，不算独立项目样本。

模型单步提议之后，要区分“想读正确来源”和“参数能读到正确字节”。可在离线归档映射中验证受限读取结果；任何多步模型诊断须先冻结请求范围和停止规则，调用仅限归档读取，不执行模型返回的构建、写入或环境操作。不能将下一步提议直接记作修复成功。

## 5. 记录与采纳标准

| 层次 | 必须记录的观测 |
|---|---|
| 工具正确性 | schema 是否通过、target 是否可解析、路径/ref 是否指向同一来源、行区间能否读到预期字节、原文是否完整封存 |
| 模型行为 | 首次读到关键原始证据之前的请求数与 token、错误派生文件读取、重复查询、未测量根因的断言、带待办检查的提前终止 |
| 完整任务 | 各 build/test 要求的状态与证据、整个任务结果、原生与独立验收是否一致；本地完成不自动等于 CI 对齐 |
| 成本与自主性 | 全部 Actor/Advisor/其他模型 token、cached/uncached 分项、无人反馈运行时间、工具/验证耗时、人类干预与资源异常 |

增加的提示文字与全部后续调用都计入，不只报告首请求长度。超时的用量/决定缺失保持 unknown，不当作 0，不补挑成功样本。

先证明原始证据可读且验收不退化，再看模型行为是否改善；小样本中无稳定收益的候选继续隔离。保留机制正确性、诊断行为和完整任务效率三类结论，不预设必须节省某个百分比。所有方案、源文件、输入/输出和结果按条件封存后才决定采纳。
